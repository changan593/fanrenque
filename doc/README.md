## 写文档的几条约定

这些不是形式要求，是踩过坑之后定的：

1. **客观结论与主观判断分开写。** 比如 `doc/08` 前三节是从数据算出来的结构，第四节起才是据此做的判断。
   这样你可以只反对结论，而不必怀疑依据。
2. **说清能力边界。** 工具做不到的事要写出来，比如 `s12` 的卷段检测只有约六成边界站得住，
   这句话必须在文档里，不能让下游误以为它可信。
3. **给出可复核的路径。** 结论后面附上产生它的脚本或原文段号（`seqN[i]`，段号 1 基），别人能自己验一遍。
4. **不确定就写「不确定」**，不要用模糊措辞把没验证的东西说得像结论。
   `【原】` 是原文有据，`【补】` 是推断补全并注明理由。
5. **一个事实只写一处。** 数字（集数、角色数、闸门阈值）以 `doc/00` 第五节的状态表和 `pipeline/config.py` 为准，
   其他文档引用而不复述；逐集的写作记录进 `doc/15`，不塞进路线图的表格单元格。
6. **变更进 `CHANGELOG.md`。** 改了规矩、改了数据口径、移动了文件，在根目录的变更记录里留一条，写清为什么。

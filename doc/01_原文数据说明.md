> **动手做分集规划前必须先看这里**，尤其是「第三部分：内容缺失」。

## 二、章节数：实际是 1222 个标题、1200 个分析单元

**不是 1232 章。** 三个数字要分清：

| 口径 | 数量 | 说明 |
| --- | --- | --- |
| 作者标注的最大章号 | 第 1213 章 | 不能当总数，因为有重号和跳号 |
| 实际章节标题行 | **1222** | 书里真实存在的章节标题 |
| 分析单元 | **1200** | 站点把部分章节合并在一页，无法拆开，合并计为一个单元 |

`1213 − 跳号 5 + 重号 14 = 1222`，对得上。

### 作者自己的编号问题（不影响内容，只是编号乱）

- **重号 14 处**：第 548、627、628、633、662、676、917、1095、1151~1156 章各出现两次，
  标题不同、内容不同，是作者发布时编号写错了。
- **跳号 5 处**：第 455、647、648、649、678 章号被跳过，前后文衔接正常，不缺内容。

因此 **`novel.json` 用文件顺序 `seq` 当唯一主键**（1~1200），
作者的章号存在 `declared_num` 里仅作参考。**后续所有环节一律以 `seq` 为准。**

## 三、⚠ 内容缺失：第 1115~1205 章之间有 41 章被截

这是本项目目前最需要你决策的问题。

站点把连续 2~3 章塞进同一页，抓取下来就是**多个标题行连排、后面只跟一份正文**。
关键在于那份正文的长度：

| 对照 | 字数 |
| --- | --- |
| 第 1110 章之后，正常独立章 | 中位 **2086** 字 |
| 2 章合并组的全部正文 | 中位 **2011** 字（应约 4172 字） |
| 3 章合并组的全部正文 | 中位 **1865** 字（应约 6258 字） |

合并组的正文量只够一章。受影响范围：**第 1115 章 ~ 第 1205 章**（全书结尾冲刺段），
共 19 组、涉及 41 个章节标题，缺约 **5.0 万字**（该段应有 8.5 万字，现存 3.6 万字）。

> **⚠ 这一节早先写的是「约 22 章的内容丢失」，那个说法不准确。**
> 它隐含「每组里有一章是完整的，另外 22 章整章没了」，但逐段核对后发现
> **每一章都被截了一段**，不是整章整章地掉。三条证据：
>
> 1. `seq1167` 正文第 16 段停在「唐真记起来了，刚才那人」——句子没写完；
>    第 18~35 段全是单个「。」共 18 行，那是站点的截断占位符，不是原文。
> 2. `seq1118` 里两章的内容都在但都只有一半：第 0~27 段是第 1115 章
>    「茶庄乞丐，独夫女孩」，第 29~61 段是第 1116 章「命河长短，螺生早晚」，
>    各约 1000 字，都不足一章。
> 3. `seq1118` 以「主事深吸一口气，走了过去」开头，「主事」此前从未介绍；
>    而前一单元 `seq1117`（第 1114 章）结束在姜赢与程百尺的书院线，
>    与茶庄毫无关系。中间断了。
>
> **所以这 41 章要整章重补，不能只补那 22 个被折叠的章号。**
> 完整清单与补齐后的处理步骤见 `doc/11_待补原文清单.md`。

### 这对项目意味着什么

按六季规划，受损段落全部落在**第六季（大结局）**。前五季的原文是完整的，
不影响第一季开工。但第六季的剧本无法只靠这份 txt 写，会出现情节断裂。

### 建议处理方式（按优先级）

1. **补一份完整原文**（最优）。从其他来源找这 41 章的完整文本，
   跑 `s1` 重新标准化即可，管道其余部分不用动。
   **要补的章号清单、以及补完之后要重跑哪些脚本，见 `doc/11_待补原文清单.md`。**
2. **暂不处理，先做前五季**。第 1~1114 章完整，够前五季用。等第六季开工前再补。
3. **接受缺失**，第六季按现有文本改编。**不推荐**——违反「严格遵守原文」原则，
   且结局断裂观众能直接看出来。

管道已经把这些单元标记为 `is_merged: true`，`merged_titles` 里记着被并进来的标题，
分析时会提示模型「不要为没有正文的标题编造情节」。**缺失的内容不会被悄悄编出来。**

## 四、其他已处理的小问题

- **正文里混入重复标题行**：第 789 单元正文中有一行缩进的 `第787章致用穷经无几语，穷经致用千百篇`，
  是抓取垃圾。已剔除并记录在该单元的 `stripped_lines` 字段，未静默丢弃。
- **文件头尾的站点推广行**：已剔除，书名/作者/简介已解析进 `novel.json` 的 `meta`。
- **第 1213 章标题为空**：作者原本就没写标题，保留为空字符串。
- **段落缩进**：原文每段以两个全角空格开头，标准化时去掉，属排版格式非内容。

## 五、`novel.json` 结构

```jsonc
{
  "meta": {
    "title": "穿越后，系统变成白噪音了怎么办",
    "author": "码字的画家",
    "source_encoding": "gb18030",
    "title_line_count": 1222,      // 真实章节标题数
    "unit_count": 1200,            // 分析单元数
    "merged_unit_count": 19,       // 受损的合并单元数
    "total_chars": 2682950
  },
  "chapters": [{
    "seq": 1,                      // ★ 唯一主键，后续一切以此为准
    "chapter_id": "ch0001",
    "declared_num": 1,             // 作者章号，有重号跳号，仅供参考
    "title": "破庙三只眼，梦里见仙班",
    "merged_titles": [],           // 被站点并进来的其他章标题
    "is_merged": false,            // true = 内容可能缺失，见第三部分
    "line_start": 6, "line_end": 69,
    "char_count": 3318,
    "paragraph_count": 63,
    "stripped_lines": [],          // 剔除的抓取垃圾，留痕
    "paragraphs": ["...", "..."]   // ★ 正文；引用里的 para 是这个数组的 1 起下标
  }]
}
```

正文只存 `paragraphs` 一份（存两份会让文件从 8.9 MB 涨到 16.8 MB）。
取整段文本用 `common.novel.chapter_text(ch)`。

`source/novel.index.json` 是同结构的轻量版（290 KB，不含正文），
做分集规划、检索、统计时加载它就够，不用啃 8.9 MB 的大文件。
